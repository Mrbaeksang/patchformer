# Data and split protocol

## Provenance and scope

Phase 0 uses only examples generated by `patchformer.data.generator`; no external dataset is downloaded, transformed, or included. The data is synthetic, executable, and intended to test the mutation pipeline. It is not evidence that a system understands naturally occurring user requests, and it must not be presented as a licensed external corpus.

Generated files belong under `data/generated/` and are ignored by Git. Small test fixtures are generated in temporary directories by tests rather than committed as opaque data files.

## Reproducibility

The generator uses a local `random.Random(seed)` and canonical JSONL serialization. The command below emits a SHA-256 fingerprint and a split manifest:

```bash
python -m patchformer generate \
  --output data/generated/phase0.jsonl \
  --examples-per-split 100 \
  --seed 20261118
```

`--examples-per-split` must be at least five so each split includes `replace`, `add`, `remove`, `noop`, and `abstain` rows. Regeneration with identical code, interpreter behavior, seed, and arguments is deterministic.

For every proposed operation, the generator computes `target_state` with the independent schema-aware patch oracle. A row is not emitted unless that dry run is valid.

## Row format

Every JSONL record contains:

| Field | Meaning |
| --- | --- |
| `id` | Deterministic synthetic row identifier. |
| `domain`, `schema_id`, `schema` | Domain and complete closed object schema. |
| `state` | Original state. |
| `instruction` | Controlled natural-language request. Values are JSON literals so the baseline can parse their type unambiguously. |
| `target_decision` | `patch`, `noop`, or `abstain`. |
| `target_patch`, `target_state` | One V0 patch or an empty patch, and the oracle-produced resulting state. |
| `task_type`, `template_id`, `split` | Audit fields for operation/template/split membership. |
| `source` | Always `synthetic-phase0` in this phase. |

## Leakage controls

This tiny benchmark uses disjoint groups rather than a random row split:

| Split | Domains / schemas | Template families |
| --- | --- | --- |
| Train | `orders-v1`, `catalog-v1` | `train-direct`, `train-rephrase` |
| Validation | `support-tickets-v1` | `validation-explicit` |
| Test | `profiles-v1` | `test-delegated` |

The generator and tests enforce that a schema ID, domain, or template ID cannot occur in more than one split. Non-boolean, non-null scalar values are namespaced or numerically ranged by split; the unit tests assert they do not overlap. Boolean and `null` values are necessarily shared finite values, so these rows alone cannot demonstrate value generalization for those types.

This is a useful smoke-test guard, not a sufficient research split design. The schemas are few, grammar families are hand-authored, and a model can still exploit artifacts. A later dataset must add many schema structures, paraphrase sources independent of label generation, de-duplication, semantic adversarial cases, and documented licenses/provenance before any generalization claim.

## External data policy

No external candidate named in the project README has been ingested. Before adding any external data, document its license, version/commit, retrieval date, transformation code, known sensitive fields, and exact split assignment here. Do not train on an evaluation benchmark or its near-duplicates.
